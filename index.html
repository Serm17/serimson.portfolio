Project 01 · Problem

AI False Negative를 먼저 확인했습니다.

실제 판매 중인 상품이 존재했지만 일반 자연어 Query에서는 “상품 없음 / 미오픈”으로 판단했습니다. 반면 정확한 상품코드나 상세 URL을 주면 가격·날짜·예약 정보를 읽을 수 있었습니다.

T1

일반 자연어 조건

상품 없음 / 미오픈으로 판단

T2

여행사명 추가

도메인을 좁혀도 실패

T3

정확한 상품코드

가격·날짜·예약 정보 확인

T4

상세 URL 직접 제공

페이지 정보 추출 가능

페이지 접근 자체보다 일반 Query를 정확한 상품·출발 Event에 연결하는 Retrieval 단계에 문제가 있을 가능성이 높다고 범위를 좁혔습니다.

Project 01 · Date-to-Event

날짜를 “보여주는 것”과 정확한 Event를 식별하는 것은 달랐습니다.

V0

기존 구조

출발일을 별도 검색 신호로 추가하지 않음.

Baseline
V1

날짜 텍스트 추가

meta description에 각 Event의 정확한 출발일을 추가.

<meta name="description"
content="2026년 12월 9일 출발. …">
V2

날짜를 Event 속성으로 분리

departureTime을 읽고 Query 날짜와 exact match.

"departureTime": "2026-11-07"
V1 · 날짜 Query

관련도 +9.1~18.6%

날짜 텍스트는 lexical relevance를 높임

V1 · 다중 Event

Exact 3/4 · 75%

11/07 Query에서 11/29 Event가 1위

V2 · 통제 후보군

Exact 4/4 · 100%

날짜 exact match를 Hard Constraint로 적용

해석

Schema 효과 ≠ 100%

구조화 필드를 읽는 Retrieval 로직까지 직접 설계한 결과

V2의 100%는 Google이나 AI Search 성능을 의미하지 않습니다. 4개 Event의 로컬 통제 후보군에서 날짜를 구조 속성으로 분리하고 exact match를 우선했을 때의 결과입니다.

Project 01 · Place Experiment

다음에는 “상품 ↔ 관광지” 관계를 따로 측정했습니다.

JOP1193 상세 페이지에는 신사이바시와 도톤보리 정보가 실제로 존재합니다. 하지만 장소 조건으로 AI에게 노랑풍선 오사카 상품을 추천하게 했을 때 JOP1193은 노출되지 않았습니다.

원본 구조 재실험

실제 페이지 구조를 보존하고 Schema만 독립변수로 비교

Schema를 넣으면 AI 노출이 0% → 100%가 된다는 뜻이 아닙니다. 이번 통제 실험에서 확인한 것은 같은 본문에서도 구조화 데이터를 읽는 시스템은 상품과 관광지의 관계를 명시적으로 식별할 수 있었다는 점입니다.
